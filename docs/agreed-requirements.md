# MarketCore: согласованные требования

Основа для проектирования сценариев и REST-контрактов. Зафиксировано по обсуждению от 09.09.2026; описывает целевое поведение, а не готовую реализацию. Поздние уточнения пользователя имеют приоритет над первоначальными ответами.

## 1. Область и общие ограничения

- В работе сценарии **1–11 и 14** по актуальному файлу [«Сценарии использования»](<scenarios.md>); нумерация ниже соответствует ему.
- **12 — регистрация покупателя, 13 — регистрация продавца:** отложены; нужные пользователи уже существуют.
- У пользователя ровно одна роль: продавец или покупатель.
- Клиент — Postman. Получение и обновление пользовательского JWT выполняются напрямую в Keycloak; запросы к сервисам идут через API Gateway. Для пользовательских операций нужен JWT; поиск по категории доступен без авторизации.
- Межсервисное общение — синхронные REST-вызовы; **Kafka сейчас не используется**. Процесс заказа продолжается независимо от первоначального HTTP-запроса клиента.
- Состав сервисов утверждён; **Camunda обязательна внутри Order Service** и управляет всем жизненным циклом заказа.
- Модель данных пока не разработана. Указанные ниже поля задают бизнес-смысл, а не окончательную схему БД.
- Платежи и доставка учебные: платёж имитируется, физическое перемещение и возврат товара не моделируются.

### Общие правила пагинации

- Во всех запросах с пагинацией (**UC-06, UC-08, UC-10, UC-14**) отсутствие параметра `page` всегда означает первую страницу.
- Для просмотра другой страницы клиент передаёт её номер в параметре `page`.
- Некорректный номер страницы (неверный формат или значение вне допустимого диапазона) приводит к ошибке; автоматической подмены номера страницы нет.
- Размер страницы — **10 элементов**, последняя страница может содержать меньше.

## 2. Ответственность компонентов

| Компонент | Ответственность |
|---|---|
| API Gateway | Вход для пользовательских запросов к сервисам |
| Keycloak | Пользовательские и служебные JWT, роли |
| User Service / UserDB | Профили, адрес доставки, идентификаторы платёжных счетов |
| Catalog Service / CatalogDB | Карточки товаров, категории, цена, доступное количество и резерв |
| Order Service / OrderDB | Заказы, их статусы, количество и зафиксированная стоимость; оркестрация Camunda, таймеры и компенсации |
| Payment Service / PaymentDB | Имитация платежей, их результаты, возвраты и выплаты |
| Внешняя заглушка доставки | Только отправляет в Order Service уведомление «доставлен» по UUID заказа; не принимает запросов создания/отмены доставки |
| Discovery Server | Обнаружение сервисов (Eureka) |
| Config Server | Централизованная конфигурация; локальный репозиторий `D:/_IntelliJ_prj/marketcore-config` |

По контейнерной схеме бизнес-сервисы имеют отдельные PostgreSQL-базы. Чужие данные получают через сервис-владелец.

Предварительные данные User Service: ФИО, email, адрес доставки покупателя и продавца, название фирмы продавца, идентификаторы счетов для оплаты и получения денег. Для имитации согласованы идентификаторы счетов вместо реквизитов банковских карт.

После оформления заказа с JWT пользователя дальнейшие шаги Camunda выполняются со служебными JWT: **Order Service как клиент запрашивает их у Keycloak**.

## 3. Каталог: сценарии 1–6 и 14

Продавец управляет только собственными карточками. Статусы карточки: **активная, скрытая**. Скрытую карточку можно только просмотреть и восстановить; остальные действия с ней запрещены.

### UC-01. Создание карточки товара с нулевым количеством

- Карточка товара принадлежит одному продавцу; общих карточек с предложениями нескольких продавцов нет.
- Обязательные сведения карточки: **название, категория, цена в BYN, описание в формате JSON**. Цена больше нуля, точность **0,01 BYN**.
- Система автоматически устанавливает **остаток и резерв в ноль**, статус — **«активная»**. Количество при создании не передаётся; начальная поставка выполняется отдельно в UC-02.
- Доступные категории хранятся в отдельной таблице CatalogDB.
- Создание карточки — отдельное действие от пополнения количества уже существующего товара.

### UC-02. Увеличение количества товара с существующей карточкой

- Продавец увеличивает доступный остаток существующей карточки на указанное количество, а не заменяет остаток абсолютным значением.
- Количество — любое **положительное целое число**, не ограниченное текущим остатком. Некорректный запрос отклоняется без изменения остатка.
- Бизнес-смысл — отправить товар на склад; новая карточка не создаётся.

### UC-03. Уменьшение количества товара с существующей карточкой

- Продавец уменьшает доступный остаток на указанное количество. Бизнес-смысл — вывоз товара со склада, а не удаление карточки.
- Количество — **положительное целое число, не превышающее доступный остаток**. При нарушении запрос отклоняется целиком, без частичного выполнения.
- Вывозить зарезервированное количество нельзя; наличие активных заказов не запрещает вывоз свободного остатка.
- Уменьшение остатка до нуля само по себе не скрывает карточку; изменение её статуса — UC-05.

### UC-04. Изменение цены товара с существующей карточкой

- Продавец задаёт новую цену товара в BYN отдельным запросом; количество не меняется.
- Цена **больше нуля**, точность **0,01 BYN**. Изменение разрешено и при нулевом остатке активной карточки.
- Новая цена применяется при последующем резервировании; стоимость уже оформленных заказов не меняется.

### UC-05. Скрытие или восстановление карточки товара с нулевым количеством

- Карточка **не удаляется физически**: запрос передаёт UUID товара и целевой статус — скрытая или активная.
- Скрытие разрешено только при одновременном выполнении условий: **остаток = 0, резерв = 0, все заказы по товару завершены или окончательно отменены**. Доставленные заказы до завершения выплаты и заказы в процессе компенсаций этому условию не соответствуют.
- Скрытая карточка исключается из использования, но остаётся доступной владельцу для просмотра в UC-14.
- Восстановление переводит карточку в активную, сохраняя **UUID, цену и остальные сведения о товаре**; само по себе не пополняет остаток.
- Повторное назначение текущего статуса возвращает **успешный ответ без изменений**.

### UC-06. Поиск товаров по категории без авторизации

- Фильтр — только категория; сортировка по наименованию; пагинация до **10 товаров на странице**.
- Возвращаются только активные карточки с доступным остатком больше нуля.
- Ответ: категория запроса, номер текущей страницы, общее число страниц, список товаров.
- Обязательные сведения о товаре в списке: название, цена, JSON-описание, категория, **доступный остаток**.

### UC-14. Просмотр продавцом своих товаров

- Возвращаются **все собственные карточки**, активные и скрытые, включая нулевой остаток; фильтр по статусу пока не включён.
- Поля: **UUID, название, категория, цена, JSON-описание, доступный остаток, резерв, статус**.
- Сначала активные карточки с сортировкой по названию, затем скрытые с сортировкой по названию. Пагинация — **10 карточек на страницу**.

## 4. UC-07. Заказ покупателем указанного числа одного товара

### Содержание и запуск

- Покупатель заказывает **одну активную товарную позицию в положительном целом количестве**, не превышающем доступный остаток.
- Postman получает **UUID заказа**; дальнейшее состояние покупатель отслеживает в общем списке своих заказов (UC-08). Завершения всего процесса в исходном запросе клиент не ждёт.
- Адрес доставки и идентификатор платёжного счёта берутся из User Service; отдельного действия покупателя для оплаты нет.
- Заказ хранит количество товара на всех этапах. Стоимость фиксируется при резервировании; изменение цены после просмотра каталога не требует уведомления или подтверждения покупателя.

### Успешный путь

1. Order Service создаёт заказ и запускает процесс Camunda.
2. Catalog Service при резервировании определяет текущую цену, переносит количество из **остатка в резерв**, фиксирует время резервирования. Заказ сохраняет согласованную стоимость.
3. По запросу Order Service Payment Service имитирует перевод **со счёта покупателя на счёт маркетплейса**.
4. После успешной оплаты заказ становится **«оплачен»**; Order Service запрашивает списание резерва в Catalog Service.
5. Catalog Service уменьшает резерв на количество заказа; Order Service учитывает это количество как **«в доставке»**, заказ переходит в соответствующий статус.
6. Заглушка доставки по UUID сообщает о доставке через внешний REST API Order Service. Только Order Service меняет статус на **«доставлен»**.
7. По таймеру Order Service выбирает доставленные заказы и при первой возможности запрашивает перевод **со счёта маркетплейса на счёт продавца**.
8. После успешной выплаты заказ становится **«завершён»**. При ошибке выплаты он не отменяется: попытки продолжаются.

### Ошибки оформления и неопределённая оплата

- Нехватка товара, явный отказ оплаты и ошибки доступности сервисов при оформлении приводят к ошибке процесса и автоматической отмене с необходимыми компенсациями.
- Явный отказ оплаты запускает отмену сразу.
- Для **неопределённого результата оплаты** предусмотрено ожидание до **15 минут**, затем запрос состояния платежа. Подтверждено, что платёж не прошёл — заказ отменяется; подтверждён успех — процесс может продолжиться.
- Таймаут запроса не доказывает отсутствие списания денег. Обработка всё ещё неизвестного результата после проверки отмечена в разделе 8.
- Если компенсация не выполнена из-за недоступности сервиса, Camunda сохраняет текущий шаг и повторяет его после восстановления. До завершения компенсаций заказ не считается окончательно отменённым.

## 5. Просмотр заказов: сценарии 8 и 10

Для покупателя и продавца одинаковые правила: **страницы по 10 заказов; сначала незавершённые, затем конечные; внутри каждой группы новые первыми по дате заказа**. Конечные — «завершён» и три статуса окончательной отмены; «доставлен» и промежуточные этапы отмены относятся к незавершённым.

### UC-08. Просмотр заказов покупателем

- Показываются **все заказы покупателя**, включая конечные статусы, с пагинацией **по 10 заказов** и общими правилами параметра `page`.
- Сведения: **UUID заказа**, дата, статус, товар, количество, **общая стоимость**, продавец, признак возможности отмены.

### UC-10. Просмотр заказов продавцом

- Продавец просматривает **все заказы на свои товары**, включая завершённые и отменённые, с пагинацией **по 10 заказов** и общими правилами параметра `page`.
- Поля: **UUID заказа, дата, статус, товар, количество, зафиксированная цена за единицу, общая стоимость, признак возможности отмены**. Сведения о покупателе не нужны.

## 6. Отмена заказов: сценарии 9 и 11

### UC-09. Отмена заказа покупателем

- Покупатель запрашивает отмену своего заказа до доставки.
- После успешных компенсаций заказ получает статус **«отменён покупателем»**.

### UC-11. Отмена заказа продавцом

- Продавец товара запрашивает отмену заказа на свой товар до доставки.
- После успешных компенсаций заказ получает статус **«отменён продавцом»**.

### Общие правила и автоматическая отмена

- Отмена доступна покупателю и продавцу товара **до доставки** через внешний REST API Order Service. После «доставлен» и «завершён» отменять нельзя обоим.
- Автоматическая отмена при ошибке — часть процесса оформления UC-07; её конечный статус — **«отменён системой»**.
- **Сразу после принятия первой отмены** (покупателем, продавцом или системой) любой повторный запрос, в том числе того же участника, возвращает ошибку **«заказ уже отменён»**, даже пока компенсации выполняются. Первый инициатор сохраняется; единственный процесс компенсаций продолжает работу. Текст ошибки не означает, что компенсации уже завершены.
- Компенсации выполняются в обратном порядке относительно уже выполненных действий: **отмена доставки → отмена оплаты → отмена резерва**. Не требуется компенсировать действие, которое не выполнялось.
- Заглушка доставки в отмене не участвует; «отмена доставки» — внутренний этап Order Service.
- При отмене оплаченного заказа деньги возвращаются **со счёта маркетплейса покупателю**.
- Количество для возврата берётся из заказа. Если товар ещё в резерве, он переносится в остаток; если резерв уже списан, количество возвращается в остаток без повторного уменьшения резерва.
- Товар сразу считается возвращённым на склад; ожидания физического возврата нет.
- После успешного завершения всех необходимых компенсаций назначается конечный статус по инициатору: **«отменён покупателем», «отменён продавцом» или «отменён системой»**.

## 7. Статусы заказа

Статусы меняет **только Order Service**; внешние участники отправляют запросы, а не изменяют данные заказа напрямую.

| Группа | Статусы |
|---|---|
| Основной путь | создан → товар зарезервирован → оплачен → в доставке → доставлен → завершён |
| Промежуточные этапы отмены | отмена доставки → отмена оплаты → отмена резерва (по необходимости) |
| Конечные результаты отмены | отменён покупателем; отменён продавцом; отменён системой |

Полную таблицу разрешённых переходов, включая ошибки и конкурентные запросы, предстоит составить при проектировании процесса.

## 8. Технические предложения для следующего этапа

Ниже — ранее обозначенные условия корректности и детали, которые ещё не оформлены в окончательные контракты. Они не заменяют согласованные бизнес-правила.

- Повторные резервирование, списание, возврат и выплата не должны повторно менять деньги/количество: определить идентификаторы операций и правила идемпотентности.
- Если после 15 минут состояние платежа недоступно или всё ещё неизвестно, продолжать уточнение, не считать неизвестность отказом; определить повторные проверки и обработку позднего успеха.
- Согласовать конкурентные отмену и доставку: позднее уведомление не должно возвращать отменяемый/отменённый заказ в доставленные.
- Включить идентификатор товара в поиск для последующего заказа; определить UUID и остальные идентификаторы в модели.
- Для UC-05 спроектировать проверку завершённости заказов через Order Service и защиту от одновременного скрытия, пополнения и резервирования товара.
- Уточнить технические детали: направление сортировки названий, порядок при одинаковых значениях сортировки, нумерацию страниц, остальные ограничения полей, JSON-схемы, URL и коды ошибок, интервалы повторов и таймер выплаты.
- Определить служебные права и проверки принадлежности ресурсов, авторизацию заглушки доставки; пользовательский JWT не должен требоваться для продолжения фонового процесса.

## 9. Результат последующих этапов

Для каждого сценария подготовить **условия и результат, последовательность шагов, диаграмму последовательности и таблицу REST-вызовов**: отправитель/получатель, метод, URL, авторизация, параметры, JSON запроса/ответа, коды ошибок и альтернативные ветки. Для заказов дополнительно согласовать переходы статусов, процесс Camunda и компенсации. Реализация сервисов — отдельная задача.
