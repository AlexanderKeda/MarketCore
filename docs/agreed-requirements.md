# MarketCore: согласованные требования

Основа для проектирования сценариев и REST-контрактов. Учтены обсуждения 09–13.09.2026; описывает целевое поведение, а не готовую реализацию. Поздние уточнения пользователя имеют приоритет над первоначальными ответами.

## 1. Область и общие ограничения

- В работе сценарии **1–11 и 14** по актуальному файлу [«Сценарии использования»](<scenarios.md>); нумерация ниже соответствует ему.
- **12 — регистрация покупателя, 13 — регистрация продавца:** отложены; нужные пользователи уже существуют.
- У пользователя ровно одна неизменяемая роль: продавец (SELLER) или покупатель (BUYER).
- Клиент — Postman. Получение и обновление пользовательского JWT выполняются напрямую в Keycloak; запросы к сервисам идут через API Gateway. Для пользовательских операций нужен JWT; поиск по категории доступен без авторизации.
- Межсервисное общение — REST по HTTP в режиме запрос–ответ; ожидание ответа может быть блокирующим или неблокирующим в зависимости от клиента. **Kafka сейчас не используется**. Процесс заказа продолжается независимо от первоначального HTTP-запроса клиента.
- Состав сервисов утверждён; **Camunda обязательна внутри Order Service** и управляет всем жизненным циклом заказа.
- Схемы описаны в документации [каталога](catalog/README.md), [профилей](user/README.md) и [заказов](order/README.md). Для Order Service спроектированы только бизнес-таблицы; технические данные Camunda, запуск и восстановление процесса добавятся отдельно. Схема Payment Service ещё проектируется.
- Один условный склад, без вариантов товара, партий и серийных номеров. Журналы движений и отдельная история изменений каталога пока не нужны.
- Платежи и доставка учебные: платёж имитируется, физическое перемещение и возврат товара не моделируются.

### Технологии и REST-контракты

- **Catalog Service — Spring WebFlux, доступ к PostgreSQL через R2DBC**. User, Order и Payment Service — Spring MVC.
- OpenAPI — исходный контракт REST API каждого бизнес-сервиса; спецификации хранятся в `docs/<сервис>/openapi.yaml` (`catalog`, `user`, `order`, `payment`). Сначала согласуется контракт, затем реализуется API.
- OpenAPI Generator создаёт DTO и интерфейсы контроллеров: реактивные для каталога, обычные для остальных бизнес-сервисов. Реализация контроллеров и бизнес-логика пишутся вручную.
- Для исходящих межсервисных вызовов из MVC-сервисов генерируются **Spring Cloud OpenFeign-клиенты**, из каталога при необходимости — **клиенты на WebClient**. MVC-сервисы могут обращаться к реактивному каталогу через Feign.
- Серверная часть генерируется по собственному контракту сервиса, клиенты и их DTO — отдельно по контрактам вызываемых сервисов. Общим источником истины служит OpenAPI, а не общий Java-интерфейс клиента и контроллера.
- Генерация выполняется при сборке Maven в `target/generated-sources/openapi` соответствующего модуля; версия генератора фиксируется в конфигурации сборки. Спецификации и настройки хранятся в Git; сгенерированный код не хранится в Git и не редактируется вручную.
- Адреса сервисов, JWT, таймауты, повторы и обработка ошибок настраиваются отдельно; генерация не заменяет согласование этих правил.

### Общие правила пагинации

- Во всех запросах с пагинацией (**UC-06, UC-08, UC-10, UC-14**) отсутствие параметра `page` всегда означает первую страницу.
- Для просмотра другой страницы клиент передаёт её номер в параметре `page`.
- Некорректный номер страницы (неверный формат или значение вне допустимого диапазона) приводит к ошибке; автоматической подмены номера страницы нет.
- Размер страницы — **10 элементов**, последняя страница может содержать меньше.

## 2. Ответственность компонентов

| Компонент | Ответственность |
|---|---|
| API Gateway | Вход для пользовательских запросов к сервисам |
| Keycloak | Пользовательские и служебные JWT, роли |
| User Service / UserDB | Полные профили покупателей/продавцов, адреса, UUID платёжных счетов |
| Catalog Service / CatalogDB | Карточки, категории, цены, доступный остаток и отдельные резервы по заказам |
| Order Service / OrderDB | Заказы, их статусы, количество и зафиксированная стоимость; оркестрация Camunda, таймеры и компенсации |
| Payment Service / PaymentDB | Имитация платежей, их результаты, возвраты и выплаты |
| Внешняя заглушка доставки | Только отправляет в Order Service уведомление «доставлен» по UUID заказа; не принимает запросов создания/отмены доставки |
| Discovery Server | Обнаружение сервисов (Eureka) |
| Config Server | Централизованная конфигурация; локальный репозиторий `D:/_IntelliJ_prj/marketcore-config` |

По контейнерной схеме бизнес-сервисы имеют отдельные PostgreSQL-базы. Чужие данные получают через сервис-владелец.

UUID пользователя в Keycloak и User Service совпадают; каталог хранит этот UUID как идентификатор продавца, без внешнего ключа в чужую БД.

После оформления заказа с JWT пользователя дальнейшие шаги Camunda выполняются со служебными JWT: **Order Service как клиент запрашивает их у Keycloak**.

### Профили User Service

- Покупатели и продавцы хранятся в одной таблице. Все поля обязательны: **UUID, имя, фамилия, email, адрес, UUID счёта, роль, время создания и последнего изменения**. Имя, фамилия и адрес — непустые строки.
- Отчество, название фирмы, телефон и статусы профиля не хранятся. Нет отдельной истории изменений; время последнего изменения обновляется при фактическом изменении данных.
- UUID профиля неизменен и совпадает с Keycloak. Роль BUYER/SELLER соответствует Keycloak и не меняется; проверка доступа использует JWT, а не только поле профиля.
- Email нормализуется до записи: нижний регистр, удаление пробельных символов по краям; внутри адреса они запрещены. Нормализованный email уникален для всех ролей и совпадает с Keycloak.
- Один адрес строкой: доставка для покупателя, отправка/возврат товара для продавца.
- У профиля один `payment_account_id` в формате UUID. Один счёт может использоваться любыми покупателями и продавцами; уникальность этой ссылки не требуется.
- Счета, балансы и операции принадлежат Payment Service; в UserDB нет банковских реквизитов карт, паролей и токенов. Межбазовых внешних ключей нет, данные профиля получают через API.
- Начальные полные профили добавляются отдельной миграцией с UUID, email и ролями существующих пользователей Keycloak и подготовленными UUID счетов. Соответствие систем проверяется при подготовке данных; локальные ограничения UserDB его не обеспечивают.
- Регистрация остаётся отложенной. Редактирование, удаление и блокировка профиля пока вне сценариев; управление доступом остаётся в Keycloak. Автоматическая синхронизация профиля с Keycloak не вводится.

## 3. Каталог: сценарии 1–6 и 14

Продавец управляет только собственными карточками. Статусы карточки: **активная, скрытая**. Скрытую карточку можно только просмотреть и восстановить; остальные действия с ней запрещены.

### UC-01. Создание карточки товара с нулевым количеством

- Карточка товара принадлежит одному продавцу; общих карточек с предложениями нескольких продавцов нет.
- Обязательные сведения карточки: **название, категория, цена в BYN, описание в формате JSON**. Цена больше нуля, точность **0,01 BYN**.
- Система устанавливает **доступный остаток в ноль**, статус — **«активная»**; записей резервов ещё нет. Поле общего резерва в таблице товара отсутствует. Количество при создании не передаётся; поставка выполняется в UC-02.
- Категории — плоский справочник с уникальными названиями в CatalogDB; у товара одна категория. Начальное наполнение заранее подготовлено.
- Карточки различаются по UUID; одинаковые названия разрешены, артикул не требуется.
- Описание — любое JSON-значение, без поиска по его полям. SQL NULL запрещён; JSON null, пустые объекты и массивы допустимы.
- Создание карточки — отдельное действие от пополнения количества уже существующего товара.

### UC-02. Увеличение количества товара с существующей карточкой

- Продавец увеличивает доступный остаток существующей карточки на указанное количество, а не заменяет остаток абсолютным значением.
- Количество — любое **положительное целое число**, не ограниченное текущим остатком. Некорректный запрос отклоняется без изменения остатка.
- Бизнес-смысл — отправить товар на склад; новая карточка не создаётся.

### UC-03. Уменьшение количества товара с существующей карточкой

- Продавец уменьшает доступный остаток на указанное количество. Бизнес-смысл — вывоз товара со склада, а не удаление карточки.
- Количество — **положительное целое число, не превышающее доступный остаток**. При нарушении запрос отклоняется целиком, без частичного выполнения.
- Вывозить зарезервированное количество нельзя; наличие активных заказов не запрещает вывоз свободного остатка.
- Уменьшение остатка до нуля само по себе не скрывает карточку; изменение её статуса — UC-05.

### UC-04. Изменение цены товара с существующей карточкой

- Продавец задаёт новую цену товара в BYN отдельным запросом; количество не меняется.
- Цена **больше нуля**, точность **0,01 BYN**. Изменение разрешено и при нулевом остатке активной карточки.
- Новая цена применяется при последующем резервировании; стоимость уже оформленных заказов не меняется.

### UC-05. Скрытие или восстановление карточки товара с нулевым количеством

- Карточка **не удаляется физически**: запрос передаёт UUID товара и целевой статус — скрытая или активная.
- Скрытие разрешено при **нулевом доступном остатке**, если все резервы товара имеют статус **«завершён» или «отменён»**. Отсутствие резервов также допускает скрытие. Проверка локальная, без запроса в Order Service.
- Скрытая карточка исключается из использования, но остаётся доступной владельцу для просмотра в UC-14.
- Восстановление переводит карточку в активную, сохраняя **UUID, цену и остальные сведения о товаре**; само по себе не пополняет остаток.
- Повторное назначение текущего статуса возвращает **успешный ответ без изменений**.

### UC-06. Поиск товаров по категории без авторизации

- Фильтр — только категория; сортировка по наименованию; пагинация до **10 товаров на странице**.
- Возвращаются только активные карточки с доступным остатком больше нуля.
- Ответ: категория запроса, номер текущей страницы, общее число страниц, список товаров.
- Обязательные сведения о товаре в списке: название, цена, JSON-описание, категория, **доступный остаток**.

### UC-14. Просмотр продавцом своих товаров

- Возвращаются **все собственные карточки**, активные и скрытые, включая нулевой остаток; фильтр по статусу пока не включён.
- Поля: **UUID, название, категория, цена, JSON-описание, доступный остаток, резерв, статус**.
- Поле «резерв» вычисляется как сумма количества записей **«в резерве» и «в доставке»**; конечные записи не учитываются.
- Сначала активные карточки с сортировкой по названию, затем скрытые с сортировкой по названию. Пагинация — **10 карточек на страницу**.

## 4. UC-07. Заказ покупателем указанного числа одного товара

### Содержание и запуск

- Покупатель заказывает **одну активную товарную позицию в положительном целом количестве**, не превышающем доступный остаток.
- **UUID заказа формирует клиент** и передаёт при создании. Любой повтор с существующим UUID — ошибка независимо от покупателя; существующий заказ в ответ не возвращается. Уникальность обеспечивает БД, включая конкурентные запросы.
- Клиент не ждёт завершения процесса; результат отслеживает в общем списке своих заказов (UC-08), в том числе после потери ответа на создание.
- Адрес доставки и идентификатор платёжного счёта берутся из User Service; отдельного действия покупателя для оплаты нет.
- Адрес сохраняется в заказе на момент оформления; последующие изменения профиля не меняют этот заказ.
- Заказ хранит количество товара на всех этапах. Стоимость фиксируется при резервировании; изменение цены после просмотра каталога не требует уведомления или подтверждения покупателя.

### Бизнес-данные заказа

- Одна таблица заказов, без отдельной таблицы позиций: UUID заказа, покупателя и товара, неизменное количество; далее UUID продавца, снимок товара, цены, адрес, счета и операции.
- При создании обязательны UUID заказа, покупателя, товара, количество, статус и даты. Остальные сведения заполняются по ответам сервисов и до этого могут быть NULL, включая заказ, отменённый системой до получения данных.
- Снимок товара: **название, категория и JSON-описание**. Продавец представлен только UUID, без имени и фамилии. Снимок и адрес после заполнения не обновляются из внешних сервисов.
- **Количество, цена единицы и общая цена — отдельные поля**. Общую цену рассчитывает приложение как количество × цену единицы; вычислений на уровне БД нет. Комиссий и скидок нет, валюта BYN.
- Доставляется только весь объём заказа; частичное исполнение приводит к системной отмене. Отдельный счётчик количества «в доставке» не хранится.
- Хранятся текущий статус, время создания и последнего фактического изменения, инициатор отмены. Истории переходов и подробной причины ошибки нет. Завершённые и отменённые заказы не удаляются.

### Платёжные ссылки

- На заказ — одна логическая оплата, максимум один полный возврат и одна выплата продавцу. Order Service генерирует и сохраняет UUID каждой операции **до первого вызова** Payment Service; пока операция не нужна, поле NULL.
- Повторы используют прежние UUID и параметры. Наличие UUID операции не доказывает успешность платежа; результат подтверждает Payment Service.
- Счёт покупателя сохраняется перед оплатой, актуальный счёт продавца — перед выплатой. После начала операции эти параметры неизменны.
- UUID счёта маркетплейса хранится в конфигурации, не в OrderDB. Его изменение не должно менять параметры повторов незавершённых операций.

### Успешный путь

1. Order Service создаёт заказ и запускает процесс Camunda.
2. Catalog Service одной транзакцией уменьшает доступный остаток и создаёт резерв по заказу с количеством, текущей ценой и временем создания. Заказ сохраняет согласованную стоимость.
3. По запросу Order Service Payment Service имитирует перевод **со счёта покупателя на счёт маркетплейса**.
4. После успешной оплаты заказ становится **«оплачен»**; Order Service запрашивает переход резерва в **«в доставке»**.
5. Catalog Service меняет статус резерва **без изменения количества и доступного остатка**. Order Service учитывает количество как «в доставке» и переводит заказ в соответствующий статус.
6. Заглушка доставки по UUID сообщает о доставке через внешний REST API Order Service. Только Order Service меняет статус на **«доставлен»**.
7. По таймеру Order Service выбирает доставленные заказы, перед выплатой получает актуальный UUID счёта продавца из User Service и запрашивает перевод **со счёта маркетплейса на этот счёт**. После начала операции её параметры сохраняются для повторов, а не заменяются новым чтением профиля.
8. После успешной выплаты заказ становится **«завершён»**; Order Service сообщает каталогу о завершении резерва. При ошибке выплаты заказ не отменяется: попытки продолжаются.

### Резерв: данные и жизненный цикл

- На заказ — один резерв; UUID заказа уникален в БД. Данные: UUID заказа и товара, количество, цена единицы на момент резервирования, статус, время создания и последнего изменения.
- Товар и исходное количество заказа неизменны. Цена резерва фиксирована; время последнего изменения обновляется только при фактическом изменении записи.
- Резервы не переиспользуются и не удаляются, включая конечные. Каталог не освобождает их по таймеру: ожиданием оплаты и командами переходов управляет Order Service/Camunda.

| Действие | Переход резерва | Доступный остаток | Количество в записи |
|---|---|---|---|
| Создание | Нет записи → в резерве | −q | q |
| После оплаты | В резерве → в доставке | Не меняется | Сохраняется |
| Завершение заказа | В доставке → завершён | Не меняется | Сохраняется для истории списаний |
| Отмена | В резерве / в доставке → отменён | +q | Обнуляется |

### Подтверждение состояния резерва

- В OrderDB хранится **последний подтверждённый Catalog Service статус резерва**: «в резерве», «в доставке», «завершён» или «отменён». До подтверждения — NULL; это не доказательство отсутствия резерва.
- Требуемое состояние определяется этапом заказа: после оплаты — «в доставке», после завершения — «завершён», при отмене — «отменён» после предшествующих компенсаций. До подтверждения допустимо временное расхождение.
- Order Service периодически повторяет необходимые команды. Сверка основана на соответствии этапов, а не равенстве названий статусов.
- Завершённый заказ остаётся завершённым при недоступности каталога; попытки завершить резерв продолжаются. Если резерв не создавался, при отмене не требуется создавать фиктивную запись.

### Атомарность и повторные команды каталогу

- Проверка и изменение остатка/резерва выполняются одной локальной транзакцией. Уникальность UUID заказа обеспечивает БД.
- Повтор создания существующего резерва возвращает сохранённый результат, не списывает товар и не меняет статус. Повтор внутреннего перехода не выполняет действие заново и не возвращает состояние назад.
- Повтор отмены отменённого резерва не возвращает товар повторно; завершённый резерв отменять нельзя.
- Пополнение и уменьшение остатка продавцом не дедуплицируются: повтор запроса считается новым действием. Это отличается от защищённых внутренних команд Order Service.

### Ошибки оформления и неопределённая оплата

- Нехватка товара, явный отказ оплаты и ошибки доступности сервисов при оформлении приводят к ошибке процесса и автоматической отмене с необходимыми компенсациями.
- Явный отказ оплаты запускает отмену сразу.
- Для **неопределённого результата оплаты** предусмотрено ожидание до **15 минут**, затем запрос состояния платежа. Подтверждено, что платёж не прошёл — заказ отменяется; подтверждён успех — процесс может продолжиться.
- Таймаут запроса не доказывает отсутствие списания денег. Обработка всё ещё неизвестного результата после проверки отмечена в разделе 8.
- Если компенсация не выполнена из-за недоступности сервиса, Camunda сохраняет текущий шаг и повторяет его после восстановления. До завершения компенсаций заказ не считается окончательно отменённым.

## 5. Просмотр заказов: сценарии 8 и 10

Для покупателя и продавца одинаковые правила: **страницы по 10 заказов; сначала незавершённые, затем конечные; внутри каждой группы новые первыми по дате заказа**. Конечные — «завершён» и три статуса окончательной отмены; «доставлен» и промежуточные этапы отмены относятся к незавершённым.

### UC-08. Просмотр заказов покупателем

- Показываются **все заказы покупателя**, включая конечные статусы, с пагинацией **по 10 заказов** и общими правилами параметра `page`.
- Сведения: **UUID заказа**, дата, статус, снимок товара (название, категория, описание), количество, **общая стоимость**, UUID продавца, признак возможности отмены.

### UC-10. Просмотр заказов продавцом

- Продавец просматривает **все заказы на свои товары**, включая завершённые и отменённые, с пагинацией **по 10 заказов** и общими правилами параметра `page`.
- Поля: **UUID заказа, дата, статус, товар, количество, зафиксированная цена за единицу, общая стоимость, признак возможности отмены**. Сведения о покупателе не нужны.
- Товар представлен сохранённым снимком. Неполученные данные не заменяются фиктивными значениями; пока UUID продавца неизвестен, заказ не попадает в его список. Возможность отмены вычисляет приложение, отдельного поля БД нет.

## 6. Отмена заказов: сценарии 9 и 11

### UC-09. Отмена заказа покупателем

- Покупатель запрашивает отмену своего заказа до доставки.
- После успешных компенсаций заказ получает статус **«отменён покупателем»**.

### UC-11. Отмена заказа продавцом

- Продавец товара запрашивает отмену заказа на свой товар до доставки.
- После успешных компенсаций заказ получает статус **«отменён продавцом»**.

### Общие правила и автоматическая отмена

- Отмена доступна покупателю и продавцу товара **до доставки** через внешний REST API Order Service. После «доставлен» и «завершён» отменять нельзя обоим.
- Автоматическая отмена при ошибке — часть процесса оформления UC-07; её конечный статус — **«отменён системой»**.
- При принятии отмены сохраняется первый инициатор: **покупатель, продавец или система**. Он не меняется и определяет конечный статус отмены; до отмены поле NULL.
- При одновременных отмене и доставке побеждает первое зафиксированное изменение. После принятой отмены доставка отклоняется; после доставки отмена запрещена. Повтор подтверждённой доставки успешен без изменений.
- **Сразу после принятия первой отмены** (покупателем, продавцом или системой) любой повторный запрос, в том числе того же участника, возвращает ошибку **«заказ уже отменён»**, даже пока компенсации выполняются. Первый инициатор сохраняется; единственный процесс компенсаций продолжает работу. Текст ошибки не означает, что компенсации уже завершены.
- Компенсации выполняются в обратном порядке относительно уже выполненных действий: **отмена доставки → отмена оплаты → отмена резерва**. Не требуется компенсировать действие, которое не выполнялось.
- Заглушка доставки в отмене не участвует; «отмена доставки» — внутренний этап Order Service.
- При отмене оплаченного заказа деньги возвращаются **со счёта маркетплейса покупателю по исходному платежу**, а не на текущий счёт из профиля.
- Для резерва «в резерве» или «в доставке» количество из записи возвращается в доступный остаток; в записи количество обнуляется и ставится «отменён». Все изменения — одна транзакция, после предшествующих компенсаций.
- Исходное количество отменённого резерва доступно из заказа; количество завершённого резерва сохраняется для связи списания с заказом.
- Товар сразу считается возвращённым на склад; ожидания физического возврата нет.
- После успешного завершения всех необходимых компенсаций назначается конечный статус по инициатору: **«отменён покупателем», «отменён продавцом» или «отменён системой»**.

## 7. Статусы заказа

Статусы меняет **только Order Service**; внешние участники отправляют запросы, а не изменяют данные заказа напрямую.

| Группа | Статусы |
|---|---|
| Основной путь | создан → товар зарезервирован → оплачен → в доставке → доставлен → завершён |
| Промежуточные этапы отмены | отмена доставки → отмена оплаты → отмена резерва (по необходимости) |
| Конечные результаты отмены | отменён покупателем; отменён продавцом; отменён системой |

Полную таблицу разрешённых переходов, включая ошибки и конкурентные запросы, предстоит составить при проектировании процесса.

## 8. Технические предложения для следующего этапа

Ниже — ранее обозначенные условия корректности и детали, которые ещё не оформлены в окончательные контракты. Они не заменяют согласованные бизнес-правила.

- UUID и правила повторов операций Order Service определены выше; гарантии однократного выполнения оплаты, возврата и выплаты предстоит реализовать в Payment Service. Повтор пользовательской отмены остаётся ошибкой, внутренний повтор компенсации не дублирует возврат.
- Если после 15 минут состояние платежа недоступно или всё ещё неизвестно, продолжать уточнение, не считать неизвестность отказом; определить повторные проверки и обработку позднего успеха.
- Реализовать согласованное правило первого зафиксированного изменения для конкурентных отмены и доставки.
- Включить идентификатор товара в поиск для последующего заказа; определить UUID и остальные идентификаторы в модели.
- Реализовать защиту от одновременного скрытия, пополнения, резервирования и отмены по правилам [схемы каталога](catalog/README.md). Проверка скрытия полностью локальная.
- Согласовать перестановку команд: отсутствие записи при отмене ещё не исключает позднее создание резерва задержавшимся запросом.
- Спроектировать техническую связь заказа с Camunda, надёжный запуск/восстановление процесса и сверку резерва. Одна бизнес-таблица не гарантирует доставку команд и восстановление после сбоя между записью заказа и запуском процесса.
- Уточнить технические детали: направление сортировки названий, порядок при одинаковых значениях сортировки, нумерацию страниц, остальные ограничения полей, JSON-схемы, URL и коды ошибок, интервалы повторов и таймер выплаты.
- Определить служебные права и проверки принадлежности ресурсов, авторизацию заглушки доставки; пользовательский JWT не должен требоваться для продолжения фонового процесса.
- При добавлении редактирования профилей определить синхронизацию email с Keycloak; сейчас соответствие обеспечивается начальными данными. Подготовка самой миграции наполнения UserDB — отдельная задача.

## 9. Результат последующих этапов

Для каждого сценария подготовить **условия и результат, последовательность шагов, диаграмму последовательности и таблицу REST-вызовов**: отправитель/получатель, метод, URL, авторизация, параметры, JSON запроса/ответа, коды ошибок и альтернативные ветки. Для заказов дополнительно согласовать переходы статусов, процесс Camunda и компенсации. Реализация сервисов — отдельная задача.
