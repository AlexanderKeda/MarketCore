# Catalog Service — схема данных

Проектная документация от 11.09.2026. Источники: [сценарии](../scenarios.md), [общие требования](../agreed-requirements.md), [контейнерная схема](../C4_Container.drawio) и последующие согласованные уточнения пользователя.

**Последние решения имеют приоритет:** у товара нет поля общего резерва; записи резервов сохраняются, количество при переходе в доставку не меняется; проверка возможности скрытия выполняется локально. В общем документе требований ещё есть прежние формулировки про счётчик резерва, списание при отправке и проверку Order Service. Этот комплект фиксирует их замену; общий документ в рамках задачи не изменяется.

## Комплект и границы

- [schema.sql](schema.sql) — PostgreSQL DDL: таблицы, ограничения, индексы, комментарии, триггеры времени изменения.
- [schema.drawio](schema.drawio) — редактируемая ER-диаграмма с полями и связями.
- Этот документ — смысл данных, правила транзакций и границы гарантий БД.

Один условный склад; без вариантов, партий, артикулов и серийных номеров. Каталог владеет карточками, категориями, доступным количеством и резервами. Профили, заказы и платежи принадлежат другим сервисам. Схема не содержит журналов движений, истории цен, таймера освобождения/очистки резервов и таблицы дедупликации запросов продавца.

## Таблицы и поля

Все поля обязательны (`NOT NULL`); первичные ключи также запрещают NULL. Значения по умолчанию указаны ниже. UUID создаёт приложение; расширения PostgreSQL не требуются.

### category — категория

| Поле | Тип | Правило |
|---|---|---|
| id | uuid, PK | Идентификатор категории |
| name | text, UNIQUE | Непустое название; точное совпадение запрещено |

Плоский справочник: одна категория содержит 0..N товаров, товар имеет ровно одну категорию. Начальное наполнение — заранее подготовленные данные; список значений пока не предоставлен, поэтому вымышленные категории в SQL не добавлены.

### product — карточка товара

| Поле | Тип / default | Смысл |
|---|---|---|
| id | uuid, PK | UUID карточки; сохраняется после восстановления |
| seller_id | uuid | UUID продавца в Keycloak и User Service совпадают |
| category_id | uuid, FK | Ссылка на category.id |
| name | text | Непустое название; дубли разрешены |
| description | jsonb | Любое JSON-значение; SQL NULL запрещён, JSON null, {}, [], строки и числа разрешены |
| price | numeric | Цена единицы в BYN, > 0, не более двух дробных знаков |
| available_quantity | bigint / 0 | Количество, доступное новым заказам, ≥ 0 |
| status | text / ACTIVE | ACTIVE — активная; HIDDEN — скрытая |
| created_at | timestamptz / CURRENT_TIMESTAMP | Создание |
| updated_at | timestamptz / CURRENT_TIMESTAMP | Последнее фактическое изменение |

Скрытая карточка имеет нулевой остаток, доступна владельцу только для просмотра и восстановления. Создание всегда с нулевым остатком; defaults в DDL не заменяют запрет передачи количества в API.

### reservation — резерв по заказу

| Поле | Тип / default | Смысл |
|---|---|---|
| order_id | uuid, PK | Один резерв на заказ; PK реализует согласованный UNIQUE(order_id) |
| product_id | uuid, FK | Ссылка на product.id |
| quantity | bigint | > 0 для всех статусов кроме CANCELLED; для CANCELLED строго 0 |
| unit_price | numeric | Неизменная цена единицы в BYN на момент резервирования |
| status | text / RESERVED | Состояние резерва |
| created_at | timestamptz / CURRENT_TIMESTAMP | Время резервирования |
| updated_at | timestamptz / CURRENT_TIMESTAMP | Последнее фактическое изменение |

Отдельный UUID резерва не нужен: адресуем его UUID заказа. У товара 0..N резервов; каждый резерв принадлежит одному товару. `order_id` и `seller_id` — логические ссылки без FK в чужие базы. Конечные резервы не удаляются и не переиспользуются. Исходное количество отменённого резерва остаётся только в заказе.

## Состояния и движения количества

| Операция | Переход | Доступный остаток | quantity в резерве |
|---|---|---|---|
| Создание | отсутствует → RESERVED | −q | q |
| После оплаты | RESERVED → IN_DELIVERY | без изменения | сохраняется |
| После завершения заказа | IN_DELIVERY → COMPLETED | без изменения | сохраняется для истории списания |
| Отмена | RESERVED или IN_DELIVERY → CANCELLED | +q | становится 0 |

Суммарный резерв для UC-14 **вычисляется**, а не хранится:

```sql
SELECT COALESCE(sum(quantity), 0) AS reserved_quantity
FROM catalog.reservation
WHERE product_id = :product_id
  AND status IN ('RESERVED', 'IN_DELIVERY');
```

Завершённые записи не входят в сумму. Нет отдельного физического складского количества. Возврат при отмене немедленный, без моделирования транспорта. Отмена резерва выполняется после предшествующих компенсаций Order Service; завершение — по его команде после завершения заказа. Сервисы взаимодействуют только через REST.

## Транзакционные правила приложения

DDL проверяет форму отдельной записи, но **не реализует бизнес-операции**. Следующие правила обязательны для будущего сервисного слоя:

1. Все операции одного товара блокируют строку `product` (`SELECT ... FOR UPDATE`) в короткой локальной транзакции. Если нужна строка резерва, порядок блокировок единый: сначала товар, затем резерв. Никаких HTTP-вызовов под блокировкой.
2. Создание резерва: проверить существующий `order_id`; для новой записи под блокировкой проверить ACTIVE и достаточный остаток, сохранить текущую цену, уменьшить остаток и вставить резерв одной транзакцией. Конфликт PK откатывает всю транзакцию, включая уменьшение. После отката повтор читает сохранённый результат. Товар и количество одного заказа неизменны по бизнес-инварианту.
3. Повтор создания возвращает существующий результат без списания и изменения текущего статуса, даже для конечного резерва. Для CANCELLED исходное количество восстановить из этой записи нельзя. Поздний повтор не активирует резерв снова.
4. Отмена: под блокировками прочитать сохранённое q, увеличить остаток на q, обнулить quantity, установить CANCELLED одной транзакцией. Повтор CANCELLED ничего не меняет; COMPLETED отменять нельзя. При отсутствии записи вернуть результат отсутствия резерва без изменения остатка. Order Service обязан исключить позднее создание после такой отмены: отсутствующая запись сама не является защитой от перестановки команд.
5. Переходы только по таблице выше; конечные статусы неизменны. Повтор достигнутого состояния не выполняет действие снова. Обработка устаревших команд не должна возвращать состояние назад. Идентификаторы, связь с товаром и unit_price после создания не меняются.
6. Скрытие: под той же блокировкой товара проверить нулевой остаток и отсутствие RESERVED/IN_DELIVERY. Если резервов нет, условие выполняется. Order Service не запрашивается. Восстановление меняет только статус. Повтор текущего статуса успешен без изменений.
7. Пополнение/уменьшение/цена разрешены владельцу только для ACTIVE. Изменение количества — положительное целое, уменьшение не больше остатка. Запросы продавца не дедуплицируются: повтор пополнения считается новым действием.

Проверки принадлежности, разрешённых переходов, неизменности цены резерва и отсутствия открытых резервов при скрытии — обязанности приложения; CHECK не сравнивает несколько таблиц. Блокировка товара общая для скрытия, резервирования, отмены и изменения количества, что исключает гонку проверки и изменения при соблюдении протокола всеми операциями.

Триггеры сохраняют created_at и меняют updated_at только при фактическом изменении остальных полей. Повтор без изменения состояния не обновляет время. История всех переходов не хранится.

## Чтение и индексы

| Сценарий / запрос | Индекс / правило |
|---|---|
| UC-01, связь категории | PK/UNIQUE category; product_category_idx поддерживает FK-проверки и выборку |
| UC-02–05 | PK product.id, изменения под блокировкой |
| UC-06 | product_public_search_idx: category_id, name, id; только ACTIVE и остаток > 0 |
| UC-14 | product_seller_list_idx: seller_id, status, name, id; ACTIVE перед HIDDEN |
| Резерв по заказу | PK reservation.order_id |
| Все резервы товара | reservation_product_idx |
| Скрытие / сумма резерва | reservation_open_product_idx: только RESERVED/IN_DELIVERY |

UC-06 возвращает название, цену, описание, категорию и доступный остаток; UUID товара нужен для последующего заказа (ранее отмеченное техническое предложение). UC-14 возвращает UUID, название, категорию, цену, описание, доступный остаток, вычисленный резерв и статус.

Списки по 10 элементов. Без page — первая страница; неправильный номер — ошибка. Нумерация с 0/1 и ответ для пустой выборки уточняются при проектировании API. Технический выбор для схемы: имя ASC, затем UUID для стабильного порядка совпадений, сравнение по collation базы. Для UC-14 сначала статус ASC, затем имя и UUID. Сортировка и сумма должны читаться в согласованном SQL-запросе; конкурентные изменения между запросами разных страниц возможны.

## Технические решения и пределы

- `text` без произвольных бизнес-лимитов; непустые названия. Уникальность категории по точному значению, без автоматической нормализации регистра/пробелов.
- `bigint`: технический максимум 9 223 372 036 854 775 807. Переполнение при пополнении/возврате — ошибка всей транзакции, не обрезание. Это предел реализации, а не согласованный бизнес-лимит.
- `numeric` без заданной precision и scale плюс CHECK: конечное положительное значение с шагом 0.01. Так лишние дробные знаки отклоняются, а не округляются типом numeric(p,2). Валюта всегда BYN, отдельного столбца нет. PostgreSQL имеет собственные технические пределы numeric/jsonb/text.
- Статусы — text + CHECK; отдельные справочники статусов и PostgreSQL enum не требуются.
- `timestamptz`: абсолютный момент времени; часовой пояс представления выбирает клиент.
- FK используют RESTRICT; каскадного удаления истории нет. Физическое удаление карточек/резервов не является операцией сервиса; DDL сам по себе не запрещает административный DELETE.

## Проверка и дальнейшая реализация

Это полный проект DDL, а не применённая миграция. Применять только в пустой изолированной PostgreSQL-базе: `psql -v ON_ERROR_STOP=1 -d <test_database> -f schema.sql`. Скрипт создаёт namespace catalog в одной транзакции; повторное применение намеренно не скрывает существующие объекты через IF NOT EXISTS.

При реализации проверить: последнюю единицу при двух заказах; дубликат order_id; rollback создания; единственный возврат при двух отменах; скрытие против резервирования; сохранение quantity при доставке/завершении; нулевое quantity при отмене; исключение конечных записей из суммы; запрет отрицательных остатков, лишней дробной части цены и SQL NULL описания; неизменность времени при повторе.

Проверка этого комплекта: статическая сверка SQL, описания и XML-диаграммы. Исполнение в PostgreSQL и проверка конкурентных операций не выполнялись: PostgreSQL-клиент/сервер в доступной среде не обнаружены. Нагрузочную пригодность индексов проверяют по реальным планам запросов после реализации.
