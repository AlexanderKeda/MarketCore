# User Service — схема данных

Проектная документация от 11.09.2026. Основа: [требования](../agreed-requirements.md), [сценарии](../scenarios.md) и последние решения по User Service. Это проект схемы, не применённая миграция.

## Комплект и границы

- [schema.sql](schema.sql) — таблица, ограничения, комментарии и триггер обновления.
- [schema.drawio](schema.drawio) — редактируемая ER-диаграмма и логические связи с другими сервисами.
- Этот документ — смысл полей, границы гарантий и использование данных.

Покупатели и продавцы хранятся в **одной таблице**, у каждого одна неизменяемая роль и только полный профиль. Регистрация (UC-12/13) пока отложена; начальные профили добавляются специальной миграцией. Сценарии редактирования, удаления и блокировки профиля не вводятся.

Последние решения уточняют общий документ: вместо ФИО — имя и фамилия, название фирмы исключено. Нет отчества, телефона, статусов профиля и отдельной истории изменений. Пароли, токены, банковские карты и балансы здесь не хранятся. Общий документ в рамках создания этого комплекта не изменяется.

## user_service.user_profile

Все поля обязательны. `id` — первичный ключ, остальные имеют `NOT NULL`.

| Поле | Тип / default | Смысл и ограничения |
|---|---|---|
| id | uuid, PK | UUID пользователя Keycloak; UUID профиля тот же. Передаётся явно |
| first_name | text | Имя, не пустое и не только пробелы |
| last_name | text | Фамилия, не пустая и не только пробелы |
| email | text, UNIQUE | Нормализован, уникален среди всех профилей, совпадает с Keycloak |
| address | text | Один непустой адрес строкой: доставка покупателю; отправка/возврат товара продавца |
| payment_account_id | uuid | Один счёт на профиль; один счёт разрешён у нескольких покупателей/продавцов |
| role | text | BUYER — покупатель; SELLER — продавец; изменение запрещено |
| created_at | timestamptz / CURRENT_TIMESTAMP | Время создания |
| updated_at | timestamptz / CURRENT_TIMESTAMP | Время последнего фактического изменения |

Тип счёта UUID — принятый технический формат учебного Payment Service. Столбец **не уникален**. Идентификатор не является доказательством права на произвольные операции со счётом; такие проверки определяются контрактом Payment Service.

Индексы создаются автоматически для PK(id) и UNIQUE(email). Дополнительные индексы на роль, адрес и счёт не добавлены: в текущих сценариях профиль получают по UUID, отдельного поиска по этим полям нет.

## Email и соответствие Keycloak

- До записи email приводится к нижнему регистру, пробельные символы по краям удаляются; внутри адреса пробельные символы не допускаются.
- Проверка синтаксиса email — ответственность приложения/подготовки данных. CHECK не является полноценным валидатором email и не подтверждает существование почтового ящика.
- UUID, нормализованный email и роль должны соответствовать Keycloak. UserDB не может обеспечить это межсистемным FK или локальным CHECK.
- Сейчас соответствие обеспечивается подготовкой и проверкой начальных данных. При появлении редактирования потребуется согласовать обновление обеих систем; автоматическая синхронизация здесь не реализована.

## Связи и использование

Межбазовых внешних ключей нет. User Service обращается только к своей БД; остальные сервисы получают профиль через API.

| Участник | Связь / использование |
|---|---|
| Keycloak | Один профиль соответствует одному UUID учётной записи; роль в таблице описывает профиль, проверка доступа использует JWT |
| Catalog Service | seller_id карточки логически ссылается на id продавца; не требует копии профиля в CatalogDB |
| Order Service, UC-07 | По UUID покупателя получает адрес и счёт. Адрес сохраняется в заказе на момент оформления |
| Order Service, UC-08 | Сведения о продавце используются для представления заказа; точный контракт будет определён отдельно |
| Payment Service | Владеет счётом, балансом и операциями; UserDB хранит только payment_account_id |
| Выплата продавцу | Актуальный счёт продавца запрашивается перед выплатой; после начала платёжной операции её параметры нельзя менять повторным чтением профиля |
| Возврат покупателю | Привязан к исходному платежу, а не к текущему счёту профиля |

Будущее изменение адреса профиля не меняет уже оформленный заказ. Данные покупателя не добавляются в список заказов продавца. Один UUID счёта может использоваться профилями обеих ролей; это не требует объединения самих профилей.

## Обновления и технические решения

- `text` без произвольных бизнес-лимитов длины. Технические пределы PostgreSQL сохраняются; лимиты API можно определить отдельно.
- Даты и ограничения согласованы с подходом схемы каталога. DDL поддерживает обновление полей, но не вводит публичный сценарий редактирования.
- Блокировка доступа остаётся в Keycloak. Отсутствие статуса в UserDB не означает мгновенного отзыва уже выданного JWT: это вопрос настройки безопасности, а не схемы профиля.
- Удаление не является операцией приложения; DDL не запрещает административный DELETE. Управление пользователями БД и правами не входит в этот комплект.

## Начальное наполнение

Будущая отдельная миграция должна вставить полные профили с UUID, нормализованными email и ролями существующих пользователей Keycloak. Счета должны соответствовать подготовленным учебным данным Payment Service; повторы UUID счетов допустимы.

Конкретные профили и счета не предоставлены, поэтому INSERT с вымышленными или реальными персональными данными не добавлены. Создание миграции наполнения и запуск её в БД — отдельный этап. Существующий импорт Keycloak этим комплектом не изменяется.
