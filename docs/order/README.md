# Order Service — бизнес-схема данных

Проект от 11.09.2026. Основа: [требования](../agreed-requirements.md), [сценарии](../scenarios.md), схемы [каталога](../catalog/README.md), [профилей](../user/README.md) и последние ответы пользователя по заказам.

## Комплект и область

- [schema.sql](schema.sql) — PostgreSQL DDL бизнес-таблицы, ограничения, индексы и комментарии.
- [schema.drawio](schema.drawio) — редактируемая диаграмма; внешние ссылки обозначены отдельно от FK.
- Этот документ — назначение данных, состояния и границы гарантий.

Проектируем **только бизнес-данные**. Таблицы Camunda, связь с экземпляром процесса, надёжный запуск процесса, расписания, технические попытки и история выполнения будут спроектированы отдельно. DDL не реализует оркестрацию. Схема не применялась к БД.

Одна таблица `order_service.orders`: один заказ содержит один товар, без отдельной таблицы позиций. Количество неизменно, частичного исполнения нет; нарушение полного исполнения приводит к системной отмене. Комиссий и скидок нет. Заказы не удаляются, истории переходов статуса нет.

Последние уточнения: UUID задаёт клиент; **любой повтор создания — ошибка**, а не возврат существующего заказа. Поля снимка, счетов и операций заполняются по мере выполнения. Статус резерва — последний подтверждённый результат, не желаемое состояние. Общие требования этим комплектом не редактируются.

## Поля orders

`Да` означает NOT NULL. Остальные поля могут отсутствовать до соответствующего этапа; NULL не заменяется фиктивным UUID или нулевой ценой.

| Поле | Тип | Обязательно | Значение |
|---|---|---|---|
| id | uuid, PK | Да | UUID заказа от клиента, неизменен |
| buyer_id | uuid | Да | UUID покупателя из JWT |
| product_id | uuid | Да | UUID заказанного товара |
| quantity | bigint | Да | Положительное исходное количество; сохраняется после отмены |
| seller_id | uuid | Нет | UUID продавца из данных каталога; имя не сохраняется |
| product_name | text | Нет | Снимок названия товара |
| category_name | text | Нет | Название категории снимка |
| product_description | jsonb | Нет | Снимок описания; JSON null допустим, SQL NULL — ещё не получено |
| unit_price | numeric | Нет | Цена единицы в BYN на момент резервирования |
| total_price | numeric | Нет | Общая цена, рассчитывается и записывается приложением |
| delivery_address | text | Нет | Снимок адреса доставки при оформлении |
| buyer_account_id | uuid | Нет | Счёт покупателя для исходной оплаты |
| seller_account_id | uuid | Нет | Счёт продавца, полученный перед выплатой |
| payment_id | uuid, UNIQUE | Нет | UUID оплаты |
| refund_id | uuid, UNIQUE | Нет | UUID полного возврата |
| payout_id | uuid, UNIQUE | Нет | UUID выплаты продавцу |
| status | text / CREATED | Да | Текущий статус заказа |
| reservation_status | text | Нет | Подтверждённый статус резерва |
| cancellation_reason | text | Нет | BUYER, SELLER или SYSTEM — инициатор принятой отмены |
| created_at | timestamptz / CURRENT_TIMESTAMP | Да | Создание |
| updated_at | timestamptz / CURRENT_TIMESTAMP | Да | Последнее фактическое изменение |

Идентификаторы пользователей совпадают с Keycloak/User Service. Товар и категория принадлежат Catalog Service; резерв адресуется тем же UUID заказа. Счета и платёжные операции принадлежат Payment Service. **Межбазовых FK нет**; история заказов не зависит от соединения с чужой БД.

Снимки заполняются при оформлении и далее не обновляются из каталога/профиля. Цена берётся именно из результата резервирования. UUID/название категории — техническое представление согласованного снимка категории. Детали получения согласованного снимка уточняются в API. Если оформление оборвалось раньше получения сведений, они остаются NULL даже у отменённого заказа.

## Деньги и доставка

- Приложение записывает `total_price = quantity * unit_price`; обе цены положительны, конечны и имеют шаг 0.01 BYN. В БД нет вычисляемых столбцов, триггеров расчёта или отдельного счётчика «в доставке».
- Оплата одна; полный возврат максимум один при отмене; выплата продавцу одна. UUID каждой операции генерирует Order Service и сохраняет **до первого сетевого запроса**. Повтор использует тот же UUID и параметры. Наличие UUID не доказывает успех операции.
- Счёт покупателя фиксируется до оплаты, актуальный счёт продавца — перед выплатой. После начала операции выбранный счёт не заменяется новым чтением профиля. Возврат связан с `payment_id`, а не с текущим счётом покупателя.
- UUID счёта маркетплейса хранится в конфигурации, не в OrderDB. Конфигурация должна сохранять согласованность повторов незавершённых операций; изменение этого счёта требует отдельного механизма перехода.
- Адрес доставки сохраняется строкой. Доставка относится ко всему quantity. Заглушка только сообщает «доставлен» по UUID; номера отправлений и частичные доставки не моделируются.

## Статусы и инициатор отмены

| Код | Значение |
|---|---|
| CREATED | Создан |
| RESERVED | Товар зарезервирован |
| PAID | Оплачен |
| IN_DELIVERY | В доставке |
| DELIVERED | Доставлен |
| COMPLETED | Завершён |
| CANCELLING_DELIVERY | Отмена доставки |
| CANCELLING_PAYMENT | Отмена оплаты |
| CANCELLING_RESERVATION | Отмена резерва |
| CANCELLED_BY_BUYER | Отменён покупателем |
| CANCELLED_BY_SELLER | Отменён продавцом |
| CANCELLED_BY_SYSTEM | Отменён системой |

Основной путь: CREATED → RESERVED → PAID → IN_DELIVERY → DELIVERED → COMPLETED. При отмене выполняются необходимые компенсации в обратном порядке; шаги для невыполненных действий пропускаются. Конечный статус отмены назначается только после необходимых компенсаций.

`cancellation_reason` фиксируется при принятии первой отмены и далее не меняется. Это классификация инициатора, не текст технической ошибки. Для обычного успешного пути поле NULL. Приложение обеспечивает соответствие конечного статуса инициатору; подробной причины сбоя и журнала переходов нет.

Отмена после DELIVERED запрещена. Одновременные отмена и доставка сериализуются: первое зафиксированное изменение побеждает. После принятой отмены каждый повторный запрос отмены возвращает «заказ уже отменён», даже во время компенсаций. Повтор зарегистрированной доставки успешен без изменения; доставка после принятой отмены отклоняется.

Признак возможности отмены вычисляет приложение из статуса, инициатора и прав участника; в таблице он не хранится. Конечные статусы не возвращаются в рабочие.

## Подтверждённый статус резерва и сверка

`reservation_status`: NULL либо RESERVED / IN_DELIVERY / COMPLETED / CANCELLED. Обновляется только после подтверждения Catalog Service. Названия статусов заказа и резерва нельзя просто сравнивать на равенство.

| Этап заказа | Действие с резервом |
|---|---|
| CREATED | Создать резерв; при неизвестном результате уточнить его наличие/состояние |
| RESERVED | Подтверждён RESERVED; ожидать оплату |
| PAID | Запросить IN_DELIVERY; до подтверждения допустимо хранить RESERVED |
| IN_DELIVERY / DELIVERED | Ожидается IN_DELIVERY |
| CANCELLING_DELIVERY / CANCELLING_PAYMENT | Не возвращать товар до завершения предшествующих компенсаций |
| CANCELLING_RESERVATION | Запросить CANCELLED; подтвердить возврат |
| COMPLETED | Добиться подтверждения COMPLETED в каталоге |
| Конечная отмена | CANCELLED для существовавшего резерва; NULL возможно, если резерв не создавался |

После выплаты заказ становится COMPLETED, а уведомление каталога может ещё ожидать повтора. Признак конечного заказа не останавливает сверку незавершённого обновления резерва. При сбоях Order Service периодически повторяет нужные команды.

**NULL не доказывает отсутствие резерва.** Для окончательной отмены после неизвестного результата создания нужны подтверждение и защита от запоздавшей команды создания. Представленная бизнес-таблица не хранит состояние каждой команды и сама эту проблему не решает; механизм будет частью последующего проектирования процесса. Аналогично, возврат денег после таймаута сначала требует выяснения результата исходной оплаты. 15 минут — ожидание перед проверкой, а не автоматическое доказательство отказа.

## Гарантии БД и приложения

- PK защищает UUID заказа от конкурентных вставок. Проверка существования перед INSERT не заменяет PK. Любой конфликт UUID — ошибка; чужие данные не возвращаются. После потери ответа покупатель ищет результат в списке своих заказов.
- UNIQUE для каждого платёжного UUID запрещает повторное использование операции в разных строках соответствующего вида. Генерация разных UUID для разных видов операций — обязанность приложения; три отдельных UNIQUE не проверяют совпадения между столбцами.
- Перед оплатой должны быть известны продавец, снимок, подтверждённая цена, итог, адрес, счёт покупателя и payment_id. Перед выплатой — выбранный счёт продавца и payout_id. Перед возвратом — исходный payment_id и refund_id.
- Приложение сохраняет неизменные UUID, quantity, снимки после заполнения и параметры начатых операций. Оно же обновляет updated_at при фактическом изменении и сохраняет created_at. Триггеры не добавлены.
- Принятие отмены/доставки и фиксация платёжных UUID требуют коротких локальных транзакций с блокировкой строки или условным обновлением. Сетевые вызовы не выполняются под длительной блокировкой.
- Согласование записи заказа, запуска процесса и повторных внешних команд не гарантируется одним DDL. Таблицы/средства для этого будут определены при проектировании Camunda, а не добавлены заранее.

## Просмотр и индексы

UC-08: свои заказы покупателя; UUID, дата, статус, товар, количество, итоговая цена, UUID продавца, возможность отмены. UC-10: заказы на товары продавца; те же сведения плюс цена единицы, без данных покупателя. Снимок товара включает название, категорию и описание. Отдельного просмотра по UUID нет. Неполученные сведения отображаются как отсутствующие, не как фиктивные значения. Пока seller_id неизвестен, заказ не попадает в список конкретного продавца.

По 10 заказов: сначала незавершённые, затем COMPLETED и три конечные отмены; внутри групп новые первыми. Индексы `orders_buyer_list_idx` и `orders_seller_list_idx` соответствуют этой сортировке. UUID — техническое дополнение для стабильного порядка одинаковых дат. Без page — первая страница, ошибочный номер — ошибка; 0/1 и пустой результат уточняются в API.

`orders_delivered_idx` помогает выбрать кандидатов на выплату. `orders_final_reservation_pending_idx` покрывает конечные заказы с известным расхождением резерва и COMPLETED без подтверждения. Он не заменяет обработку активных процессов и неизвестных результатов команд; периодичность и полный алгоритм сверки вне текущей бизнес-схемы.
